Verified operating model

One memory system. Two deliberate lanes.

KraneBrain serves work. BrittBrain serves personal knowledge. Claude and Codex use the same names everywhere, while each machine has one clear operational role.

Markdown remains canonical GBrain provides retrieval No GBrain dependency on BrittBot or OpenClaw

01 / Topology

Canonical architecture

The MacBook is the sole writer for the work index. The Mac Mini provides always-on work retrieval and is the sole host for the personal index.

02 / Retrieval lanes

Names carry the boundary

Claude and Codex see the same two tools on either machine. The tool name makes the intended knowledge domain explicit.

Work / gbrain

KraneBrain

Meetings, decisions, people, projects, and operational context for work.

  • Canonical dataKraneBrain Markdown vault
  • IndexSupabase Postgres
  • WriterMacBook only
  • ReadersMacBook and Mac Mini

Personal / brittbrain

BrittBrain

Books, workouts, podcasts, life records, and durable personal knowledge.

  • Canonical dataBrittBrain Markdown vault
  • IndexLocal PostgreSQL on the Mini
  • HostMac Mini only
  • ReadersMacBook and Mac Mini

03 / Machine roles

One owner for every background job

Each index has a single maintenance authority. This avoids duplicate ingestion, conflicting writes, and unnecessary laptop load.

Machine Work lane Personal lane What it does not do
MacBook Edits KraneBrain; runs the sole work ingestion and maintenance process; queries Supabase through gbrain. Queries the Mini through brittbrain. Does not maintain a duplicate BrittBrain index.
Mac Mini Keeps an Obsidian Sync mirror and queries the existing Supabase index through a query-only gbrain profile. Hosts BrittBrain GBrain and its local PostgreSQL index through brittbrain. Does not ingest KraneBrain or act as a second work-index writer.

04 / Work away from laptop

The Mini retrieves; Supabase answers

Work questions remain available through the always-on Mini without turning the Mini into a second ingestion host.

  1. Ask Codex or Claude on the Mac Mini

    The client routes the work question to the MCP connection named gbrain.

  2. The query-only profile searches Supabase

    It reads the same KraneBrain index used by the MacBook and does not import from the mirrored vault.

  3. Results return with the work source boundary intact

    The MacBook remains the only process that changes or refreshes the work index.

05 / Guardrails

Designed to stay simple

The architecture deliberately avoids extra agents, duplicate databases, and automated cross-domain federation.

No agent dependency

GBrain does not depend on BrittBot or OpenClaw. The Mac Mini is infrastructure, not an autonomous memory agent.

No second work index

The Mini reuses the existing Supabase work database. It does not create or maintain a local KraneBrain database.

No automatic federation

Work and personal retrieval remain separate by default. The caller chooses gbrain or brittbrain.

Markdown remains recoverable

KraneBrain and BrittBrain vaults remain the durable source of truth. GBrain databases are derived retrieval indexes.

Freshness has one owner

When the MacBook is offline, the Mini can still retrieve the last indexed work state. New work notes become searchable after MacBook maintenance resumes.

Files remain reachable

Obsidian Sync mirrors KraneBrain to the Mini, so the notes remain locally available even though the Mini work profile is query-only.
